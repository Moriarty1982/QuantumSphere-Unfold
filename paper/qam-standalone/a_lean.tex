\section{The Lean formalisation}\label{app:lean}

Two Lean~4 packages accompany QAM. The record checker \texttt{qam/lean} uses only the Lean core library, without Mathlib. The modules of the abstract machine import nothing from Mathlib either, although the package \texttt{formal} that contains them depends on it for other modules.

\paragraph{The record checker} (\texttt{qam/lean}). The module \texttt{QAM.Provenance} formalises derivation trees with status, frame
and inputs (Section~\ref{sec:properties}, frames). The module \texttt{QAM.QamFile} contains the one-pass checking function for
exported records and the proofs of what an accepted record satisfies; the executable \texttt{qamcheck} is a short driver around it. The table maps the results of Section~\ref{sec:properties} to the
Lean names.

Four limits of this correspondence should be stated. The tree theorems compare the root of a tree with its leaves. The record theorems
are proved for the checking function applied to a list of lines; the parser that turns text lines into that list, and the driver that
applies the same step function while reading a file, are not verified. The \texttt{link} theorems hold line by line; that no hash
occurs twice in a whole record is tested by the checker but not stated as a theorem. And the clause of
Theorem~\ref{thm:inputs}\,(iii) that no ancestor is an input entry is proved in this article by hand only. The second half of
Proposition~\ref{prop:links}, that a changed entry changes its hash, is a property of MD5 and is not formalised. Lean does
not compute MD5; the script \texttt{qamhash.py} does.

\paragraph{The abstract machine} (\texttt{formal/QSFormal}). The module \texttt{Store} formalises the store, its admissibility, the
instruction set (store, link, snapshot, rollback, scrub, export) and the three-way execution of Section~\ref{sec:requests}; the module
\texttt{StoreProgress} adds the progress statements.
\begin{center}
\small
\begin{tabular}{@{}p{0.36\textwidth}p{0.56\textwidth}@{}}
\toprule
Proposition~\ref{prop:machine} & Lean theorem(s)\\
\midrule
(i) admissibility preserved & \texttt{exec\_preserves}, \texttt{run\_preserves}, \texttt{exec\_cont\_admissible}\\
(ii) no halt & \texttt{exec\_ne\_halt}; outcomes characterised by \texttt{exec\_cont\_iff}, \texttt{exec\_reject\_iff}\\
(iii) atomicity & \texttt{exec\_atomic}\\

\end{center}
The formalisation follows the definitions in the main text of the research project, with simplifications: addresses are natural
numbers, the log carries no pointers, and cloning and merging of stores are not included. The Python executor has a different
instruction set (it includes \texttt{READOUT} and \texttt{RUN\_TAPE}), and that it behaves like this model is not proved.
